Analyze your implementation, including stopping conditions and any algorithm parameters (e.g., the gap sequence for shell sort). You can show this on screen or written on paper.
- Update the program

Measurements illustrate the theoretical analysis; they do not prove a complexity bound.

## Example
- Let's say that as part of **A2** you've implemented **exponential search**, **bubble sort** and **shell sort**. Let's say the user wishes to see the behaviour of these algorithms in the worst case. For bubble sort, your program will generate five reverse-sorted lists (e.g., lengths `500`, `1000`, `2000`, `4000` and `8000` elements). Choose and justify the inputs separately for shell sort and exponential search; for searching, use sorted lists. Then, you will time each algorithm using a module such as [timeit](https://docs.python.org/3/library/timeit.html), and display the results on the console.
- In case the algorithm takes too long/little, you can adjust the list lengths. For very slow algorithms (e.g., permutation sort), you may use smaller, non-doubling sizes or fewer sizes; explain your choice. Randomized bogosort has no finite worst-case running-time bound: explain this instead of attempting to measure its worst case, and use an iteration or time limit for its other experiments.
- When comparing sorting algorithms on the same input pattern, use identical starting values. Give every sorting call, including every repetition, a fresh copy of the original input so that an earlier call does not leave it already sorted.
- Prepare inputs and copies before starting the timer. Exclude list generation, copying, sorting in preparation for searching, and correctness checks from the timed interval. Check the results outside that interval.
- Make sure the algorithms do not perform additional work (e.g., displaying on the console, as required for **A2**)
- Display the results (list length, mean search or sort duration, and the ratio to the duration for the previous size) in a way that allows users to see the progression of the runtime (e.g., you can use the example from the lecture notes). With doubling sizes, quadratic growth suggests a ratio of approximately `4`; linear growth suggests approximately `2`. Small execution times and timing noise can obscure these trends, especially for logarithmic searches.
